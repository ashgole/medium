# JavaScript Closures: Finally Explained in Plain English (5-Min Read)

*A closure is when a function remembers the variables around it, even after its parent function has finished running.*

Ever wondered how a JavaScript function manages to remember variables from a parent function that has already finished running and disappeared from the call stack?

If closures have ever confused you, you're not alone.

Most tutorials explain closures using terms like "lexical environment" and "execution context," which can make a simple concept feel much harder than it actually is.

So let's throw the jargon out for a moment.

In this article, we'll break down closures using a simple **What, When, Why, and Example** approach so you can understand them without the headache.

---

# 1. What Is a Closure?

Imagine a function is a traveler leaving home.

When you define an inner function inside an outer function, the inner function doesn't leave empty-handed.

It carries references to the variables from its surrounding scope that it needs.

Think of it as a **backpack 🎒**.

```text
+-------------------------------------------------------------+
|  outerFunction() runs and eventually finishes              |
|                                                             |
|  innerFunction walks away holding its "Backpack" 🎒         |
|                                                             |
|  Backpack: [ score, secretKey, username ]                   |
|                                                             |
|  Whenever innerFunction runs later, it can access them.    |
+-------------------------------------------------------------+
```

Normally, you might think that when a function finishes, its local variables disappear.

But if another function still references those variables, JavaScript keeps them available.

That's a **closure**.

In simple terms:

> A closure is a function together with access to the variables from its surrounding scope.

Here's a tiny example:

```javascript
function createCounter() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}

const counter = createCounter();

console.log(counter()); // 1
console.log(counter()); // 2
console.log(counter()); // 3
```

`createCounter()` has already finished running, but the returned function can still access `count`.

That's the closure.

---

# 2. When Should You Use Closures?

You probably use closures every day without even realizing it.

Here are some common situations where they are useful.

### Private Variables

Closures can keep data private and expose only the functions you want the outside world to use.

### Function Factories

You can configure a function once and create reusable functions from it.

For example:

```javascript
function createDiscountCalculator(discount) {
  return function (price) {
    return price - price * discount;
  };
}

const tenPercentOff = createDiscountCalculator(0.10);
const twentyPercentOff = createDiscountCalculator(0.20);

console.log(tenPercentOff(100));  // 90
console.log(twentyPercentOff(100)); // 80
```

Each returned function remembers its own `discount`.

### Timers and Event Handlers

Closures are extremely common with asynchronous JavaScript.

```javascript
function greetLater(name) {
  setTimeout(() => {
    console.log(`Hello, ${name}!`);
  }, 1000);
}

greetLater("Ash");
```

The callback still has access to `name` when the timer executes later.

### React

Closures are also very important when working with React.

Event handlers, effects, callbacks, and other functions created during rendering can capture values from that particular render.

Understanding closures helps explain many React concepts, especially things like **stale closures**.

---

# 3. Why Do Closures Matter?

Closures give us a way to keep state private without putting everything into global variables.

Imagine this:

```javascript
const account = {
  balance: 100
};

account.balance = -99999;
```

Any code that has access to `account` can modify `balance`.

That's not ideal.

With closures, we can keep the variable inside a function and expose only controlled operations.

This gives us:

* Better encapsulation
* Private state
* Cleaner modules
* Less reliance on global variables
* Reusable function factories

### How JavaScript Handles It

Conceptually, you can think about it like this:

```text
[ Call outer() ]
       |
       v
[ Create local variables ]
       |
       v
[ Return inner() ]
       |
       v
[ outer() finishes ]
       |
       v
[ inner() still references outer variables ]
       |
       v
[ Variables remain available ]
```

The important idea is that the JavaScript engine can keep variables alive as long as they're still needed by reachable code.

You don't need to memorize how the engine stores every detail internally.

Just remember:

> If a function still has access to a variable from an outer scope, that variable can remain available even after the outer function has finished.

### The Trade-off

Closures are useful, but they aren't completely free.

If a long-lived function keeps references to large objects or lots of data, those objects may remain in memory as long as they're reachable through that closure.

So the rule is simple:

**Use closures naturally, but avoid unnecessarily keeping large amounts of data alive.**

# 4. Practical Examples

## Example 1: The Classic Loop Trap

This is a popular JavaScript interview question.

Consider this:

```javascript
// ❌ Problem: var is function-scoped

for (var i = 1; i <= 3; i++) {
  setTimeout(() => {
    console.log(`Count: ${i}`);
  }, 1000);
}

// Output:
// Count: 4
// Count: 4
// Count: 4
```

Why does this happen?

Because `var` is **function-scoped**, not block-scoped.

All three callbacks refer to the same `i`.

By the time the timers execute, the loop has already finished and `i` is `4`.

The simple fix is:

```javascript
// ✅ Recommended: let is block-scoped

for (let i = 1; i <= 3; i++) {
  setTimeout(() => {
    console.log(`Count: ${i}`);
  }, 1000);
}

// Output:
// Count: 1
// Count: 2
// Count: 3
```

With `let`, each loop iteration gets its own binding for `i`, so each callback sees the expected value.

This is one of those JavaScript concepts that becomes much easier once you understand closures and scope together.

## Example 2: Building Private State

Let's build a small bank account.

First, here's the problem with exposing everything publicly:

```javascript
// ❌ Public state

const badAccount = {
  balance: 100
};

badAccount.balance = -99999;

console.log(badAccount.balance); // -99999
```

Anyone with access to the object can directly change the balance.

Now let's use a closure:

```javascript
// ✅ Private state using a closure

function createAccount(initialBalance) {
  let balance = initialBalance;

  return {
    deposit(amount) {
      if (amount <= 0) {
        return "Amount must be positive";
      }

      balance += amount;
      return `Balance: $${balance}`;
    },

    withdraw(amount) {
      if (amount > balance) {
        return "Insufficient funds";
      }

      balance -= amount;
      return `Balance: $${balance}`;
    },

    getBalance() {
      return `$${balance}`;
    }
  };
}

const myAccount = createAccount(100);

console.log(myAccount.deposit(50));
// Balance: $150

console.log(myAccount.withdraw(30));
// Balance: $120

console.log(myAccount.getBalance());
// $120

console.log(myAccount.balance);
// undefined
```

Notice something important:

There is no `myAccount.balance` property.

The `balance` variable lives inside `createAccount()` and is accessible to the returned methods through a closure.

The outside code can't directly modify it.

That's a simple example of **encapsulation using closures**.

# 5-Second Cheat Sheet

**What is a closure?**

→ A function that retains access to variables from its surrounding scope.

**When should you use closures?**

→ Private state, function factories, callbacks, timers, event handlers, and many JavaScript patterns.

**Why are closures useful?**

→ They let functions maintain access to state without putting that state in the global scope.

**Common interview trap?**

→ `var` inside asynchronous loops can cause every callback to see the same final value.

**Most important thing to remember?**

→ The inner function can still access variables from its outer scope even after the outer function has finished.

---

## Takeaway

Closures aren't magic.

They're simply a natural result of how JavaScript's **scope** and **functions** work.

A function can remember and access variables from the environment where it was created.

Once you understand that, many JavaScript concepts become much easier to reason about.

So the next time someone asks you:

**"What is a closure?"**

You can keep it simple:

> **A closure is a function that remembers and can access variables from its surrounding scope, even after the outer function has finished executing.**

Keep the **backpack 🎒** analogy in mind, and closures become a lot less scary.
